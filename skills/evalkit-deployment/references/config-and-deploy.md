# Config and deployment

## Trying evalkit first

To see evalkit work before deploying it, run the try-it stack in `../try/`,
following [Try locally](../../evalkit-docs/try-locally.md). It uses the same
image and your own LLM, and runs a sample agent through an SDK run with traces.

## Deployment shape

One prebuilt docker image: server + built UI + skills + cost-map snapshot. This skill ships a [`docker-compose.yml`](../docker-compose.yml)
that runs `server` + `postgres`; it pulls the image from
`EVALKIT_IMAGE` (set it to the image you were given — registries differ per
client, so there is no default). Postgres holds everything evalkit stores
except bytes: users, workspaces, agents, cases, experiments and scores.
External services are first-class:

- An existing Postgres: set `db.url` and drop the bundled postgres service.
- Blob storage: `file://` (mount a volume) or `s3://`-style URL.

The **UI is part of the same server image** and served at the server root —
there is no separate UI deployment. At runtime the FastAPI app serves
`/assets` and returns `index.html` for every non-`/api` path (so client-side
routes survive a refresh); deploying the image deploys the UI. Note it ships
only in the image, not the CLI wheel — a server run from the wheel serves the
API but 404s at `/`.

## Setup sequence (exact commands)

```bash
# Copy this skill's deployment files into your deploy dir, then edit them:
cp <this-skill-dir>/config.example.yaml config.yaml   # fill in: blob, judge_default, credentials
cp <this-skill-dir>/docker-compose.yml .
# Env referenced by config.example.yaml + compose: EVALKIT_IMAGE (the server
# image you were given), POSTGRES_PASSWORD, EVALKIT_ENCRYPTION_KEY, and every
# env var named under credentials: (JUDGE_LLM_API_KEY, OURAGENT_DEV_KEY, ...).
# First start: EVALKIT_ADMIN_PASSWORD (8+ characters, at most 72 bytes)
# creates the admin user; a server with no admin and no
# EVALKIT_ADMIN_PASSWORD refuses to start. Put these in a .env
# file next to docker-compose.yml.
# With db.migrate_on_start: true in config.yaml (see "Migrations on start"),
# this one command starts everything and migrates:
docker compose up -d
# Without it, migrate before starting the server — it verifies the schema and
# refuses to boot when it is missing or outdated:
#   docker compose up -d postgres
#   docker compose run --rm --no-deps server evalkit db upgrade --config /etc/evalkit/config.yaml
#   docker compose up -d
uv tool install --reinstall evalkit --index http://localhost:8020/api/cli/simple   # the CLI, from the server
evalkit login --url http://localhost:8020   # admin / $EVALKIT_ADMIN_PASSWORD
evalkit users add <teammate>                    # optional, admin only
evalkit workspaces create dev                    # admin only; then prod
evalkit workspaces members add dev <teammate> --role writer   # or --role reviewer
evalkit agents create <name> --workspace dev --harness-url https://agent-dev.internal/evalkit/v1
evalkit sync <cases-dir>/<suite> --workspace dev   # your case YAML; uploads its fixtures too
evalkit harness check <name>@dev                 # all declared capabilities must pass
evalkit run <suite>@dev --agent <name>@dev                   # first experiment
```

The UI serves at the server root (http://localhost:8020); the server's own
API reference is at `/docs` (Swagger, generated by FastAPI). Config flow: the
compose file bind-mounts your `config.yaml` to `/etc/evalkit/config.yaml` and
passes secrets as environment variables, which `env:VAR` values resolve at
load.

**Health check:** the server exposes `GET /api/health` → `{"ok": true}` (200
once the app is up). Use it for load-balancer / Kubernetes liveness and
readiness probes rather than `/` (which returns the SPA `index.html`).

## Migrations on start

`db.migrate_on_start: true` makes the server run `evalkit db upgrade` itself
before it starts serving. It holds a Postgres advisory lock while it
migrates, so replicas that start together migrate one at a time and the rest
find the schema current.

- Turn it on for a single-node compose deployment: `docker compose up -d` is
  then the whole start, and an upgrade is pull the new image and `up -d`
  again.
- Leave it off when a separate step runs migrations, for example a Helm
  pre-upgrade hook, or when you want to back up and run a migration by hand.
  A release whose notes call for a maintenance window needs that window whatever this setting says.
- There is no downgrade. Back up the database before you pull a new image
  with this on, the same as before a manual `db upgrade`.

## Self-managed Postgres

To use an existing Postgres instead of the bundled `postgres` service, create
a dedicated role and database, then point `db.url` at it and drop the
`postgres` service (and its `depends_on`) from `docker-compose.yml`. evalkit
keeps all its records in this database; back it up like any production
database.

As a Postgres superuser (e.g. `psql -U postgres`):

```sql
CREATE ROLE evalkit WITH LOGIN PASSWORD '<password>';
-- Postgres 16+ (and managed Postgres like RDS/Aurora/Cloud SQL, where the
-- admin is not a true superuser) requires you to be a member of a role to
-- create objects owned by it. Grant it to yourself first:
GRANT evalkit TO CURRENT_USER;
CREATE DATABASE evalkit OWNER evalkit;
-- `evalkit db upgrade` creates tables in the public schema. On Postgres 15+
-- non-owners cannot create in `public` by default, so make evalkit own it:
\connect evalkit
ALTER SCHEMA public OWNER TO evalkit;
```

`env:` resolves a whole value only (it can't be embedded mid-string), so keep
the password out of `config.yaml` by putting the entire URL in an env var —
exactly as the bundled compose does for the built-in postgres:

```yaml
# config.yaml
db:
  url: env:EVALKIT_DATABASE_URL
```

```bash
# .env (async psycopg driver, host reachable from the server container)
EVALKIT_DATABASE_URL=postgresql+psycopg://evalkit:<password>@<host>:5432/evalkit
```

Run `evalkit db upgrade` (via `docker compose run ... server evalkit db upgrade`
or the CLI) to create the schema, exactly as in the setup sequence above.

## config.yaml

Start from `config.example.yaml`. Any string value supports `env:VAR`
indirection, resolved at load time — keep secrets out of the file.

| Section | What it holds |
|---|---|
| `server` | `base_url` (used in links the CLI prints), optional `accent_color` (any CSS colour, e.g. `'#dc2626'`; tints the web UI so each environment is told apart at a glance) |
| `db` | Postgres URL (`postgresql+psycopg://…`); optional `migrate_on_start` (default `false`, see below) |
| `blob` | one blob URL: `fixtures/sha256/<sha256>` (case input files), `trajectories/`, `artifacts/` |
| `judge_default` | the judge an experiment uses unless the run picks another: OpenAI-compatible `base_url`, `model`, `reasoning_effort: high`, `max_tokens: 32768`, `concurrency`. Its key is `credentials.judges[base_url]`. Use a reproducibility-tested model. |
| `credentials` | the only place API keys are configured. `agents` and `evaluators` are keyed by reference (`ouragent@dev`), `judges` by judge `base_url` (or `env:NAME` naming the variable that holds it). Values are `env:NAME` and are read when a call needs them. A server run whose agent has no entry fails to start with "no credentials.agents entry for <ref> in the server config"; a missing evaluator key sends no header (the far side's 401 shows as a run error); a missing judge key stops the run before the first case. |
| `encryption_key` | Fernet key that encrypts trace source API keys. The server refuses to start without it once a trace source exists. `evalkit trace-sources rekey` re-encrypts after a change. |
| `sentry` | optional: `dsn`, `environment`, `traces_sample_rate` (default `0.0`, errors only), `max_request_body_size` (default `never`; `small` up to 1 KB, `medium` up to 10 KB, `always`; bodies can hold client case and trajectory data). With it, the server reports unhandled errors, 500 responses and error logs to Sentry, tagged with release `evalkit@<version>`. IPs, cookies and sensitive headers are never sent. |
| `cost_map` | `bundled` (snapshot in the image) or a path/URL override |
| `auth` | `token_ttl_hours` for UI/CLI tokens |
| `mcp` | optional `oauth`: `issuer`, `jwks_uri`, optional `audience` (default `<server.base_url>/mcp`), `algorithm` (default `RS256`), `scope` (default `evalkit:read`: the scope name your identity provider grants for read access). With it, `/mcp` also accepts that identity provider's JWTs carrying `scope`; evalkit login tokens work either way |
| `otel` | collector limits, below |
| `limits` | request body caps, below |

### Request body limits

The server reads request bodies as a stream and stops at the cap. A request
over a cap gets `413` before the server reads past it, and the server logs
the route, the cap and the size received.
Fixture uploads and trajectory or artifact writes stream straight to blob
storage, so a large upload does not sit in server memory. Downloads of
fixtures, experiment blobs and stored run files stream too. Sending a
fixture to a harness as a multipart upload first copies it to a temporary
file in the server's temp directory (`/tmp` in the image). Give it room for
the fixtures of the runs in flight: each agent's `max_concurrent_runs`,
summed over the agents running at once, times the largest case's fixtures.
In Kubernetes, `/tmp` on the container counts against the pod's ephemeral
storage, and running out gets the pod evicted: mount an `emptyDir` at `/tmp`
and set `ephemeral-storage` requests and limits to cover it. Run workspace
files and folder zips stream too, from blob storage or the harness, one
chunk at a time.

On S3 or another object store, add a bucket lifecycle rule that aborts
incomplete multipart uploads after a day and expires objects under
`fixtures/staging/` after a day. A client that disconnects, or a server that
stops, in the middle of an upload can leave either behind, and evalkit does
not clean them up.

| Key | Default | Applies to |
|---|---|---|
| `limits.fixture_upload_bytes` | 500 MB (`524288000`) | one fixture file uploaded by `evalkit sync` |
| `limits.experiment_blob_bytes` | 500 MB (`524288000`) | one trajectory or artifact a local or SDK run writes |
| `limits.case_upload_bytes` | 50 MB (`52428800`) | the case YAML files of one `evalkit sync` or `evalkit lint` |
| `limits.request_bytes` | 10 MB (`10485760`) | every other request body (JSON) |
| `otel.max_batch_bytes` | 16 MB | one collector export, see below |

The `413` detail names the cap and its key, and the CLI prints it, e.g.
`fixture upload is larger than the 500 MB limit (server config limits.fixture_upload_bytes)`.
Raise the key in `config.yaml` and restart the server to allow larger
bodies. A proxy in front of the server may have its own, smaller limit.

Agents, remote evaluators, trace sources, workspaces and their reviewers
are not in `config.yaml`. They live in the database and are managed with
the CLI or the UI:

| Thing | Create with | Notes |
|---|---|---|
| Agent | `evalkit agents create <name> --workspace dev --harness-url …` | omit `--harness-url` for a code-driven agent; `--trajectory-source otel` needs `--mapping`; run settings such as `--max-concurrent-runs` (min'd with the harness's own limit), `--run-timeout`, `--stop-grace` are flags; `evalkit agents edit` changes them |
| Remote evaluator | `evalkit evaluators create <name> --workspace dev --endpoint … --kind score` | `--kind gauge` for measurements; runs use the evaluators in the agent's workspace |
| Trace source | `evalkit trace-sources create <name> --url … --api-key-env VAR` | admin only to create; any user can import from it (see below) |
| Shared workspace | `evalkit workspaces create <name>` | admin only |
| Writer / reviewer | `evalkit workspaces members add <ws> <user> --role writer\|reviewer` | admin only |

Boundary rule — config vs capabilities: config answers "where and how do I
reach you"; capabilities answer "what can you do once reached". Where both
express a limit (concurrency), evalkit takes the minimum.

## Outbound URLs and network egress

- The server calls URLs that admins set:
  - a shared agent's `harness_url`
  - remote evaluator endpoints
  - trace source URLs
  - the judge base URL
- evalkit does not block internal addresses: localhost, private ranges, or
  cloud metadata addresses such as `169.254.169.254`.
- Only admins can set URLs the server calls. The server never calls URLs from
  personal workspaces.
- The server does not follow redirects on these calls, so a harness or
  evaluator cannot bounce it to another address.
- One more outbound call: the LiteLLM cost map. The server image bundles it,
  so the default setup makes no call. A server run from source without it
  fetches it from `raw.githubusercontent.com`, and a `cost_map.source` set to
  a URL is fetched at start. Allow that host if you restrict egress, or set
  `cost_map.source` to a file path.
- If this matters on your network, restrict the server's egress there, e.g.
  block `169.254.169.254` and any internal ranges the server does not need.

## Upgrades

Pull the new image → back up the database → with `migrate_on_start`, start
the new server (it migrates first); without it, stop or hold the new server →
`evalkit db upgrade` (same compose-run pattern as setup) → start the server → developers update the CLI with the install command
or `evalkit update` (every CLI call nudges them until they do), which also refreshes the skills in client repos that
vendor them.

## CLI for the deployer

The server image already contains the CLI — `docker compose run --rm server
evalkit …` works with no local install. The image also serves its own wheel,
all unauthenticated: as a Python package index at `/api/cli/simple` (so
`uv tool install --reinstall evalkit --index <server url>/api/cli/simple`
installs or updates the CLI in one command), as a file at `GET /api/cli/wheel`
(checksum at `GET /api/cli`), and on the `/docs/install` page in the UI with
copyable commands. A proxy in front of the server must pass `/api/cli/*`
without auth. For what to hand every other developer on the team, follow the
**evalkit-usage** skill.
Client suites that need input files register them per that skill's
`references/suite-fixtures.md`.


## OpenTelemetry collector and trace sources

The server accepts OTLP/HTTP spans at `POST /api/otel/v1/traces` (protobuf
or JSON, gzip accepted) with a user token or an agent token, and converts a
session's spans to ATIF on demand. The optional `otel` block:

```yaml
otel:
  settle_seconds: 10        # a session is settled when its newest span arrived longer ago than this
  max_batch_bytes: 16777216 # one export request; 413 beyond it
  max_session_bytes: 402653184 # span attributes one session read loads; 413 beyond it
```

An agent whose trajectories come from spans is created with
`--trajectory-source otel --mapping mapping.json`. The mapping's `answer`
(`root`, a span name, or `<span name>.<output key>`) and `exclude_spans`
say where the answer comes from and which spans to leave out. The agent's
`--trajectory-wait` (default 60 seconds) is how long a run waits for its
session to settle, and `--provides key=true` sets capability flags evalkit
cannot infer from spans.

`settle_seconds` and `trajectory_wait_seconds` answer two different
questions. `settle_seconds` is the server's rule for "this session is
complete": no span has arrived for that long, so the batch exporter (which
ships every 5 s by default) has nothing left. `trajectory_wait_seconds` is
the runner's patience: how long one run keeps polling for that settled
state before recording the trajectory as `partial` (root span seen) or
`unavailable` (nothing seen) and moving on. Raise the first when spans
arrive in bursts with long gaps; raise the second when the agent keeps
emitting for a while after it answers.

The two size limits protect the server, not the database. An export
request over `max_batch_bytes` (16 MiB, after gzip) gets `413` and its spans
are dropped. Building one session's trajectory (for a run, `evalkit traces
check` or the Mappings tab) needs memory in proportion to the span
attributes it loads, so a session over `max_session_bytes` (384 MiB) gets
`413` with its size and the limit instead of being loaded. LLM spans carry
the full input of each call, so a long agent session can store hundreds of
MB. A build loads that input only for the first LLM call of each agent and
subagent, and the limit counts only what a build loads, so the stored size
of a session can be far above the limit.

The server's memory limit is what these defaults are sized for. They keep
two session reads at once (the most the server runs together) inside a
2 GiB container: one read of the largest session allowed peaks at about
0.6 GB above the idle server (about 200 MB). With less memory, lower
`max_session_bytes`; raise it only with more memory. The server builds
sessions in its own process, so a server killed for memory drops every
request it is serving until it restarts; with a single replica, every route
returns 502 until then.

Agents with large spans should export in small batches with a longer
timeout: `OTEL_BSP_MAX_EXPORT_BATCH_SIZE=16` and
`OTEL_EXPORTER_OTLP_TIMEOUT=60` (seconds in Python; other SDKs read
milliseconds). The server's Tracing docs page and the connect-traces skill
give the agent's developers the same settings.

Spans land in the `spans` table; mappings in `span_mappings`; agent tokens
are rows in `auth_tokens` with `kind = agent`. History comes from a trace
source registered with `evalkit trace-sources create`:

- `evalkit traces import <agent> <session id> --source <trace source> --project <name>`
  pulls one session.
- `evalkit traces import <agent> --source <trace source> --project <name> --since <time>
  [--until <time>]` pulls every trace that started in the range as a job on the
  server, `otel.import_page_traces` traces per request to the source. Jobs are rows
  in `trace_imports`; `evalkit traces imports <agent>` lists them, and a failed or
  stopped job continues with `--continue`. A range import needs an active mapping
  with a `session_id` rule.
- The agent page's Import tab does both.

Trace sources are server-wide. Any user can import from any trace source
into an agent they can write, so developers can mine cases from traces on
their own. This means the source's API key is shared with every user in
effect: anyone can import any project that key can read. Give each trace
source a key scoped to only the projects you are happy to share with every
user. Imported traces are readable by every user too, since every user can
read every workspace.

Retention for `spans` is not built yet; size the database for the traffic you
point at the collector and the history you import.
